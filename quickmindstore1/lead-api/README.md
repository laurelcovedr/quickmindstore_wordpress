# Store1 inquiry receiver — compatible API, not deployed

This separate Python 3.12+ / SQLite service is a compatible API implementation; it is not a WordPress plugin and does not create WooCommerce orders. It can run alongside a staging WordPress host or a standalone Store1 server. No changes to quickmindstore.com. No real SMTP, server permissions or production database verified.

## Run and connect

Use a dedicated Store1 staging VM/container, HTTPS reverse proxy and private persistent disk. Configure secrets via the server's secret manager, never frontend code or Git. Required: `QM_HASH_SECRET`, `QM_ADMIN_TOKEN` (independent random secrets, >=32 chars), `QM_LEAD_DB` (absolute path outside webroot), `QM_ORIGIN` (exact Store1 origin). Start `python server.py --port 8081` with a service manager. Bind is localhost. Map HTTPS `/lead-api/` to `http://127.0.0.1:8081/`. Alternatively set `window.QM_LEAD_API` before app.js/localized.js to an HTTPS API base URL (no trailing slash). API defaults disabled by absence of a running endpoint; it never falls back to pretending an email draft was received.

Ship `dist/lead-client.js`, modified `app.js`, `localized.js`, `tracking.js` together. The shared module adds required inquiry consent and optional analytics consent to English dynamic forms and seven localized static forms. ES module loading requires HTTP(S), not file://, and CSP must permit this same-origin module and the API connection. Existing language page generator continues loading localized.js; no SEO/language/source-key rewrite required.

POST `/v1/leads`: JSON fields `submission_id` (UUID retained for retries), `customer_type` (home/clinic/distributor), `language` (en/zh-CN/es/fr/de/ja/ko/id), `name`, `email`, `country`, `organization`, `quantity`, `notes`, `payment`, `consent:true`, `website:''`, `source_page`, `source_cta`, `source_reference`, `utm` (five existing UTM keys). All attribution is visitor-provided marketing metadata, not authoritative identity. Response only confirms `stored:true` after transaction commit. Timeout/invalid response/storage failure keeps entries and permits retry. Duplicate identical request within 24h receives the same ID; changing details creates a new ID. No existing lead/customer existence is disclosed by email lookup. A reused submission ID with different payload returns 409.

## Notifications and operations

Configure `QM_SMTP_HOST`, `QM_SMTP_PORT` (default 587), `QM_SMTP_FROM`, `QM_NOTIFY_TO`, and optionally `QM_SMTP_USER`/`QM_SMTP_PASSWORD`. Configure recipient on the server after verification, not from visitor input. Run `python server.py --notify` periodically (e.g. every minute) as a **single** worker. Pending/failed notifications retry independently of form submissions. STARTTLS certificate validation is required. `smtp_accepted` means SMTP accepted the message, not delivered/read; verify delivery in the real provider. A crash after SMTP acceptance but before state commit can produce duplicate notifications (stable lead ID/Message-ID identifies them). No automatic visitor email to avoid public email abuse. Keep approved sender, SPF/DKIM and provider delivery monitoring as deployment checks.

GET `/v1/export.csv` and `/v1/summary` require `Authorization: Bearer <QM_ADMIN_TOKEN>`. Never embed this token in the public site. Export includes server UTC time, contact fields, customer type, locale, page, CTA, UTM and notification state; spreadsheet formula injection is neutralized. Restrict administrator access at reverse proxy/VPN; rotate token and use secure export handling. For page/CTA/campaign reporting, group exported unique lead IDs. Dedupe prevents retries inflating counts.

Optional centralized `/v1/events` accepts only consented page views and inquiry clicks, with no contact fields or UTM query strings. Event IDs prevent duplicate retries. DNT/GPC suppress analytics. Optional form checkbox enables analytics for the current in-memory page session after successful submission; a future global consent banner can call `window.qmSetAnalyticsConsent(true/false)` without touching contact records. `tracking.js` reports subsequent SPA page changes. `/v1/summary` includes counts, not unique visitors. Since visitors consenting late and nonconsenting leads differ, these counts cannot establish a full-site conversion rate. Use a reviewed global consent banner/analytics policy before measuring a denominator across the whole acquisition funnel. Historical browser-only counts are not uploaded or merged.

## Security and privacy

Exact Origin allowlist, JSON-only requests, 16 KiB body cap, contact validation/length limits, honeypot, 30 requests/minute/IP for leads/events, HMAC IP hashes deleted after one hour; no raw IP/contact/access-token logs. SQLite parameterization and transaction lock protect concurrent dedupe. Origin/honeypot are not bot authentication: enable edge rate limits/WAF, body/time limits and verified challenge if abuse requires it. Proxy must not cache POST/export, and must preserve Origin. Current limiter sees direct peer IP: for a reverse proxy enforce visitor-aware rate limits at the edge; do not blindly trust X-Forwarded-For. Single-process stdlib HTTP server is intended for independent testing and low-volume staging behind that proxy, not a scaled deployment.

Data minimization: do not solicit patient medical records. Inquiry consent is separate from marketing/analytics. Add final controller/privacy notice with contact for access/deletion before public launch. SQLite file is chmod 0600; use dedicated service account, encrypted persistent volume/backups, TLS and least-privilege access. Plain SQLite is not encrypted at rest by this module. Keep DB, secrets, exports, logs and backups out of Git/webroot. Configure retention with `python server.py --purge-days 180` (example, requires operator-approved retention); it removes old leads/events and vacuums SQLite. Deletion/access requests must be handled by the authorized operator including SMTP copies, exports and backups. Purge cannot delete external copies automatically.

## Verification and acceptance

From quickmindstore1: `node scripts/test-attribution.cjs`; `node scripts/test-interactions.cjs`; `node scripts/test-lead-client.cjs`; `python -m unittest discover -s lead-api -v`.

API tests execute actual local HTTP requests and temporary SQLite writes: all 8 languages x 3 types, source fields/UTM, dedupe/idempotency conflict, input rejection, origin, authorization, CSV safety, consented events, storage failure, missing SMTP, simulated SMTP failure/retry and rate limits. Client tests use a DOM/fetch harness (not a real browser): confirmed/unconfirmed response, network failure, retained data, stable retry keys, attribution and locale coverage. Existing interactions test now checks route/form rendering; API client behavior has its own suite. SMTP test uses a fake transport, never sends real mail.

Before deployment acceptance: stage all files, run real browser tests on all language forms/mobile/modal, confirm CSP/CORS/timeouts; submit uniquely tagged test leads and verify actual staging DB rows/UTC/export; verify authorized notifications in real recipient inbox and provider logs; test fail/retry after stopping SMTP/storage, deletion/retention and backup restoration. Browser QA and actual deployment are pending. Existing separate browser QA draft PR is not superseded. Do not merge into live store or report mail delivery/database live until those checks pass.
